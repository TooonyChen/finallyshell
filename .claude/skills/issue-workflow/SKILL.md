# Issue-driven workflow

The owner of this repository works like this: every change starts as a
GitHub issue that already says how to solve it, every PR belongs to an
issue and closes it on merge, and every merge is a squash merge. The owner
usually writes in Chinese; answer in their language, but keep everything
that goes into git or GitHub (branches, commits, PR titles and bodies,
issues) in English, as CLAUDE.md says.

Why it matters to them: issues are the record of what was decided and why,
so they want the thinking (options, trade-offs, the recommendation) in the
issue, not lost in a chat. A PR that says `Closes #N` closes its issue the
moment it's merged, so the issue list is always the true list of open work.

The loop has seven steps. Small fixes go through all of them too, just
faster.

## 1. Understand and research

Before writing anything, find out what the real problem is and what the
options are:

- Read the code involved, and the docs of the libraries it uses (MyGo's
  source and docs are in the Go module cache: `go list -m -f '{{.Dir}}'
  github.com/egoist/mygo`). Prefer what the stack already provides over a
  new dependency, and say so when it does (for example, MyGo ships a code
  editor in `ui/editor`).
- For a bug, find the root cause, or at least the likely places, before
  proposing a fix. A test that reproduces it is the best evidence.
- Think of two or three ways to do it, pick one and say why. Name what is
  out of scope.
- Ask the owner only about decisions that are really theirs (product
  choices such as a default folder or whether to keep a panel), and put a
  recommendation next to each question. Everything else, decide.

When the owner asks "how would we do this?", answer with the plan first
and offer to open the issue; when they say to go ahead, write it.

## 2. Write the issue

One issue per independent piece of work. Use
`mcp__github__issue_write` (load it with ToolSearch). The title is a
Conventional Commit line, as the PR's will be: `fix(app): ...`,
`feat(sshx): ...`, `docs: ...`. Label it `bug`, `enhancement` or
`documentation`. Body:

```markdown
## Problem            (or ## Bug, with what happens and what's expected)

## Proposal           (the chosen solution; the options considered and why
                       this one; libraries or APIs to use)

## Details            (edge cases, data model, UI text, platforms)

Not in this issue: ...

## Acceptance criteria

- [ ] tests that prove it (a bug's test fails before the fix)
- [ ] both languages (locales/en.json, locales/zh-Hans.json)
- [ ] screenshots for UI changes

---
_Generated by [Claude Code](https://claude.ai/code)_
```

Big work gets a tracking issue with a checklist of child issues and the
order between them ("after #4 and #5"). A bug or idea found while working
on something else becomes its own issue rather than a change slipped into
an unrelated PR.

## 3. Plan the order

Before starting several issues, sort them:

- Which can start now, which wait for another issue (a data model, a
  window helper), which are blocked outside the repo (upstream libraries:
  say so, don't work around it if the issue says not to).
- Which touch the same files. Parallel work is fine; give each one clear
  ownership of its area and tell them who else is working nearby.
- Start the ones without blockers first, in parallel; start the next ones
  as their blockers merge.

Tell the owner the plan in a short table before dispatching.

## 4. Branch and implement

- Branch from the latest `origin/main`, named by Conventional Branch:
  `feature/...`, `bugfix/...`, `hotfix/...`, `release/...`, `chore/...`.
  One issue, one branch, one PR.
- Commits follow Conventional Commits, imperative, lowercase, no period,
  about 72 characters, with the session's attribution trailer lines.
- Follow "Working on the code" in CLAUDE.md: `gofmt`, `go vet ./...`,
  `go tool mygo vet`, `go test -race ./...`, new UI text in both locales
  plus `go tool mygo generate`, goroutines change state only through
  `App.post`. Run the live SSH tests when a test sshd is available
  (`FINALSHELLY_TEST_SSH`).
- For UI changes, take tester screenshots in English and Simplified
  Chinese and look at them yourself before calling it done.

To run several issues at once, dispatch one subagent per issue in an
isolated worktree, in the background, all in one message. Write their
prompts from `references/subagent-prompt.md`: it holds the template and
what a good prompt must say (the issue text, what's on main, who owns which
files, the checks, the PR rules, what to report).

## 5. Open the PR

Use `mcp__github__create_pull_request` against `main`.

- Title: a Conventional Commit line. It becomes the squash commit's title.
- Body: follow `.github/pull_request_template.md` (Summary, Testing).
- Link the issue, always:
  - `Closes #N` when the PR does everything the issue asks. GitHub then
    closes the issue on merge. One line per issue if it closes several.
  - `Refs #N` when it's only part of the issue, or a follow-up to an
    issue that is already closed. Say what's left.
  - No issue yet? Open one first (step 2), even for a small follow-up
    found in review.
- Testing says what was run, what tests were added, and what wasn't
  tested (real macOS/Windows windows, real keychains, and so on).
- End the body with the attribution footer the session asks for.

## 6. Review

The coordinator reviews every PR before merging, including those of
subagents:

- Fetch the branch, read the diff, and check it against the issue's
  acceptance criteria.
- Check it merges with the current main (`git merge-tree --write-tree
  origin/main origin/<branch>`). Run the checks on the merged result in a
  scratch worktree, not just on the branch, since main moves while
  others merge.
- Look at the screenshots. For a bug fix, confirm the new test fails
  without the fix (revert the fixed file in the scratch worktree and run
  the test).
- Look for what tests don't catch: work on the UI thread that could block,
  data that could be lost or overwritten, secrets that could be written to
  disk, security checks (host keys, listen addresses), platform behavior.
- Send findings back to the PR's author (`SendMessage` to the subagent)
  in one message: what to change, why, and the rebase if needed. Don't
  post GitHub review comments unless the owner asks for them.

## 7. Squash-merge and follow up

- Merge with `mcp__github__merge_pull_request`, `merge_method: "squash"`,
  and `expectedHeadSha` set to the head you reviewed. Never a merge commit
  or a rebase merge.
- Commit title: the PR title plus ` (#<PR>)`. Commit message: a short
  paragraph of what changed, then `Closes #N` (or `Refs #N`), then the
  attribution trailers.
- After a merge, tell the subagents still working what changed on main
  that touches them, so they rebase once rather than conflict later.
  Merge in the order that makes the fewest rebases (a PR that others
  build on goes first).
- Report to the owner: what merged, what was fixed in review, what is
  still open or blocked, and caveats such as "not tried on a real Mac".
- Anything found after a merge is a new issue and a new PR. A merged PR
  is never reused.
